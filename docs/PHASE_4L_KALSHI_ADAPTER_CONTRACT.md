# Phase 4L: Kalshi Adapter Contract

## Goal

Define a strict read-only Kalshi adapter contract using the existing repo's schema, fixture, builder, validator, and test patterns. No HTTP client. No network calls. No credentials. Contract-definition phase only — the contract describes what operation categories are permitted and what is explicitly forbidden; it does not implement any network access.

## Deliverables

### ID Helper

`packages/strategy-dsl/src/kalshi-readonly-adapter-contract-id.js`

SHA-256 deterministic ID, prefix `krac_`, 32 hex chars. Inputs: `adapterName | adapterVersion | allowedOperationCount | forbiddenOperationCount`.

### Builder

`packages/strategy-dsl/src/build-kalshi-readonly-adapter-contract.js`

Self-contained — no fixture file reads. Exports:
- `allowedOperationCategories` — `["market_discovery", "market_metadata", "orderbook_snapshot_read"]`
- `forbiddenOperationCategories` — 16 explicitly blocked categories (order placement, cancellation, position/portfolio/balance/account access, credential handling, authenticated trading, deposit, withdrawal, recommendations, picks, signals, decisions, bankroll sizing, live execution)
- `buildKalshiReadonlyAdapterContract(options)` — returns the full contract object

Safety flags enforced at build time:
- `paper_only: true`
- `live_execution_allowed: false`
- `order_placement_allowed: false`
- `credentials_allowed: false`
- `network_client_allowed: false`
- `adapter_mode: "read_only_contract_only"`
- `contract_scope: "contract_definition_only"`

### Schema

`packages/strategy-dsl/schemas/kalshi_readonly_adapter_contract.schema.json`

JSON Schema draft 2020-12, `additionalProperties: false`. All safety flag fields are `const`-constrained. `allowed_operation_categories` items are `enum`-constrained to the three permitted categories.

### Validator

`packages/strategy-dsl/src/validate-kalshi-readonly-adapter-contract.js`

**Design note:** `validateObservationBoundary` is intentionally not called. The shared boundary guard flags field names containing the word "credential" as forbidden keys, which conflicts with the required safety flag field `credentials_allowed: false`. All safety guarantees are enforced by purpose-built checks:

- `validateNoUnknownFields` — strict field whitelist (reuses boundary-guard helper)
- `validateCoreFields` — schema version, timestamps, adapter name/version/mode, source system, contract scope
- `validateSafetyFlags` — all five boolean flags enforced to their required values
- `validateDeterministicId` — recomputes expected ID and rejects any mismatch
- `validateOperationCategories` — allowed set whitelist check + required forbidden set membership check + overlap rejection
- `validateStatusAndReason` — status enum, `reason_code: VALIDATION_PASSED`, non-empty reason
- `validateForbiddenImplementationFields` — recursive scan for 35 dangerous field names: `fetch`, `axios`, `http_client`, `websocket`, `socket`, `api_key`, `api_secret`, `token`, `secret`, `bearer`, `auth_token`, `private_key`, `poll`, `polling_interval`, `cron`, `timer`, `interval`, `order`, `order_id`, `order_request`, `trade_request`, `signal`, `recommendation`, `pick`, `decision`, `bankroll`, `bankroll_allocation`, `kelly_fraction`, `position_size`, `expected_value`, `edge`, `base_url`, `endpoint_url`, `live_url`

## What this phase does not include

- No HTTP client (fetch, axios, got, node:http, node:https)
- No WebSocket, EventSource, or polling
- No Kalshi API credentials, tokens, API keys, or secrets
- No `.env` files or environment variable loading
- No live Kalshi endpoint URLs
- No order endpoints, execution logic, or bankroll actions
- No signals, recommendations, picks, decisions, or edge calculations
- No changes to existing validators, builders, or fixtures
